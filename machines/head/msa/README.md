# Managed full ColabFold CPU databases

For serial preparation of a frozen target panel on one worker, including
`bio-msa install --json PANEL.json`, see [PANEL.md](PANEL.md).

This component installs the complete classic CPU database reference onto the managed 3000 decimal GB volume at `/mnt/bio-msa-databases/colabfold`. It keeps UniRef30 2302 representatives and expansion sequences, ColabFold environmental 202108 representatives and expansion sequences, the August 2025 representative taxonomy/pairing correction, PDB100 230517 sequences, template A3M FFDB, and the complete current divided and obsolete mmCIF mirror. Production readiness always requires every dataset and the complete CPU indexes. Download and conversion stages retain partial progress without qualifying it for inference.

The immutable candidate pins are ColabFold `c35de0221f4d297a39edf4cf292ba2832e321edc`, MMseqs2 release 18 `8cc5ce367b5638c4306c2d7cfc652dd099a4643f`, and MMseqs2-App backend `01365aa4735539ba95b417f73fb5326c77410394`. These combine the published release-18 CPU guidance with the pinned official backend. They are **not an attestation of the current public service's deployed binary**. CPU ordering follows classic TSV conversion (`FAST_PREBUILT_DATABASES=0`); upstream warns that its newer fast prebuilt databases can change CPU results. The complete backend-generated MsaJob and PairJob commands remain unchanged. [ColabFold guidance](https://github.com/sokrypton/ColabFold/blob/c35de0221f4d297a39edf4cf292ba2832e321edc/README.md), [database setup](https://github.com/sokrypton/ColabFold/blob/c35de0221f4d297a39edf4cf292ba2832e321edc/setup_databases.sh), [backend pipelines](https://github.com/soedinglab/MMseqs2-App/blob/01365aa4735539ba95b417f73fb5326c77410394/backend/worker.go).

Run installation on a preparation worker with the dedicated database volume mounted read/write. The 16 GB head is unsuitable. The installer rejects less than 120 GiB **available** RAM; this is a minimum preflight, not a guarantee that every index fits. Managed installation, preparation and serving automatically select available FIN-02 x86 compute with at least 768 GiB RAM and an instance-price ceiling of $13/hour; spot offers are eligible. `--spot` restricts selection to spot offers, and `--worker TYPE` overrides automatic selection. The launch rechecks the price and project budget. Full API preparation also checks available RAM on the worker because upstream's much smaller batch-RAM guidance does not describe this API's complete `.idx`/mmap execution. A cold-disk, lower-RAM API deployment requires separate measurement without changing the search. Source archives total about 242 GB before extraction. Serial working allowances are conservative planning estimates, not measured final footprints; actual free-space checks stop before exhaustion and require additional storage rather than reduced datasets. [Official MSA server](https://github.com/sokrypton/ColabFold/blob/c35de0221f4d297a39edf4cf292ba2832e321edc/MsaServer/README.md).

```sh
# Application code comes from the orchestrator's verified worker-local bundle.
export MSA_TOOLS_ROOT=/mnt/bio-shared/envs/msa-tools-v1
export MSA_DB_ROOT=/mnt/bio-msa-databases/colabfold
python3 "$TOOLS/msa/databases.py" plan --root "$MSA_DB_ROOT"
# Optional: stage all ~242 GB of verified archives on the existing head first.
python3 "$TOOLS/msa/databases.py" download --root "$MSA_DB_ROOT"
# On a preparation worker, bootstrap the exact tools before conversion/indexing.
source "$TOOLS/msa/tools.sh"
# Optional: convert on a worker with at least 56 GiB available RAM; no indexes yet.
python3 "$TOOLS/msa/databases.py" convert --root "$MSA_DB_ROOT" --threads 8
# Full indexing/installation requires a separately sized high-RAM worker.
python3 "$TOOLS/msa/databases.py" install --root "$MSA_DB_ROOT" --threads 32
python3 "$TOOLS/msa/databases.py" validate --root "$MSA_DB_ROOT"
python3 "$TOOLS/msa/server.py" config --root "$MSA_DB_ROOT" \
  --results /mnt/bio-shared/cache/msa-api --output "$OUT/msa-server.json"
"$MMSEQS_SERVER" -local -config "$OUT/msa-server.json"
```

`tools.sh` needs Linux x86_64 AVX2, curl, tar, flock, and coreutils. It verifies pinned archive SHA256 values, executable hashes and reported commits before reuse. Archive hashes were recorded from the pinned upstream HTTPS downloads; they are not independent signed checksums. Extracted licenses accompany the tools. Python uses only the standard library; database installation additionally requires rsync, awk, and the ordinary shell utilities invoked by MMseqs2. Default mmCIF mirror is PDBe's rsync endpoint on port 873; `--pdb-mirror` and `--pdb-port` permit another full wwPDB mirror.

The optional `download` action needs Python, curl and the mounted persistent volume; it does not need `tools.sh`, large RAM or a rented worker. It uses the same immutable manifest and installation lock, reserves space for **all remaining archives plus 16 GiB**, resumes interrupted transfers, and records source hashes in `.downloads.json`. Hashing uses 16 MiB chunks. It performs no extraction, conversion, index creation or mmCIF mirroring, and never creates a production-installation receipt. Run full `install` afterward on suitable compute; the verified staged archives are reused. If a full installation already exists, `download` validates it and skips staging.

The optional `convert` action performs the same classic TSV extraction and `tsv2exprofiledb` conversion for both sequence corpora, the same PDB100 `createdb`, and the current UniRef taxonomy update, then stops before `createindex`. It preserves all representatives, members, headers and expansion alignments under `.staging/<component>/built`. `.conversions/<component>.json` and `.conversions.json` record commands, source hashes, file checks, exact representative/member counts, decoded residue totals and maximum lengths; they explicitly set `production_ready: false`. Counts stream the numeric MMseqs index using its decoded lengths, including for compressed databases. Running `install` afterward verifies and reuses these files; only unfinished indexing and the remaining template/coordinate installation proceed. A changed converted file fails validation before index creation. Verified sources and conversion intermediates remain until full component promotion.

Taxonomy is applied before the conversion checkpoint. Release 18's index builder packs sequences, headers and expansion alignments; pairing reads the separate base mapping, so this ordering does not replace or embed different taxonomy. An actual official API pairing replay after the new conversion/index path matched the earlier taxonomy-after-index fixture byte for byte. Final component receipts preserve the original conversion and resumed index command history after staging cleanup. [Index construction](https://github.com/soedinglab/MMseqs2/blob/8cc5ce367b5638c4306c2d7cfc652dd099a4643f/src/util/indexdb.cpp), [pairing mapping lookup](https://github.com/soedinglab/MMseqs2/blob/8cc5ce367b5638c4306c2d7cfc652dd099a4643f/src/util/pairaln.cpp).

Conversion rejects less than **56 GiB available RAM** before loading tools or modifying storage. A nominal 64 GB worker is a candidate only if that actual check passes; the 16 GB head is unsuitable. This threshold follows the pinned implementation's in-memory numeric indexes: the environmental corpus has about 739 million members, and overlapping readers plus ordering arrays can account for roughly 41 GiB before buffers and file-backed pages. It is a source-based allowance, not a measured guarantee for the full conversion. It does not lower the full-index build requirement or change index/search settings. The resulting actual residue totals are intended to size that later build. [Pinned conversion workflow](https://github.com/soedinglab/MMseqs2/blob/8cc5ce367b5638c4306c2d7cfc652dd099a4643f/data/workflow/tsv2exprofiledb.sh), [database reader](https://github.com/soedinglab/MMseqs2/blob/8cc5ce367b5638c4306c2d7cfc652dd099a4643f/src/commons/DBReader.cpp), [database writer](https://github.com/soedinglab/MMseqs2/blob/8cc5ce367b5638c4306c2d7cfc652dd099a4643f/src/commons/DBWriter.cpp), [corpus counts](https://pmc.ncbi.nlm.nih.gov/articles/PMC9184281/).

Stdout is final JSON and progress goes to stderr. If a systemd unit sets `StandardOutput=file:/path/to/downloads.json`, also set `StandardError=journal` explicitly; systemd's inherited stderr would otherwise mix progress into that JSON file.

Downloads resume and verify exact source length and the upstream-published MD5 where available, then retain local SHA256 provenance. The taxonomy patch has no separately published checksum in the source listing: it uses pinned URL/length, gzip CRC verification, and the first verified download's locally recorded SHA256. A changed archive fails rather than silently replacing a snapshot. Downloads, conversions, and index creation resume under one installation lock. Components promote atomically only after structural validation. Only their verified archives and owned staging intermediates are then removed; interrupted builds retain their sources. No final receipt exists until every component validates. [Published source files and checksums](https://colabfold.mmseqs.com/), [taxonomy change](https://github.com/sokrypton/ColabFold/wiki/MSA-Server-Database-History).

`manifest.json` fixes the build definition; `.msa-databases.json` is the complete-installation receipt; `.components/*.json` retain source hashes, commands and file checks. The current mmCIF mirror is frozen at installation completion, with gzip CRC checks and every decoded structure's SHA256 recorded in `mmcif/mmcif-content.jsonl.gz`. Subsequent validation walks every mmCIF path and size, hashes the compact content manifest, and checks first/last 64 KiB fingerprints of MMseqs files. It does not reread coordinate contents or every byte of large MMseqs files, so it does not detect arbitrary same-size interior corruption. The full coordinate metadata walk can still incur NFS latency. Preserve the small receipts, conversion statistics and content manifest on retirement. A new dated version requires a fresh managed root rather than mutating an existing snapshot.

`server.py config` validates the installation and writes a localhost-only configuration (`127.0.0.1:8080`, no URL prefix, one local worker, serial stages), a sibling `.provenance.json`, and JSON containing `config`, `namespace`, and the exact server `command`. Database receipts, executable hashes and configuration determine the persistent results namespace, because upstream ticket IDs alone do not encode that provenance. Both `/ticket/msa` and `/ticket/pair` work; environmental pairing stays disabled as in the published server configuration. Template retrieval includes selected A3M profiles and current/obsolete mmCIF coordinates. Keep raw result tarballs, generated `msa.sh`/`pair.sh`, template bundles and model-native prepared files: row ordering, insertions, chain mapping and templates are part of any parity comparison. [Official configuration](https://github.com/sokrypton/ColabFold/blob/c35de0221f4d297a39edf4cf292ba2832e321edc/MsaServer/config.json).

Export `MMSEQS_NUM_THREADS` before generating configuration and starting the backend; the effective count and relevant OpenMP environment also participate in the namespace and provenance. Release 18 reads this variable and then calls `omp_set_num_threads`, so `OMP_NUM_THREADS` alone does not replace it. The managed recipe limits API searches to 16 threads; index creation may use a separate thread count. [Pinned parameter handling](https://github.com/soedinglab/MMseqs2/blob/8cc5ce367b5638c4306c2d7cfc652dd099a4643f/src/commons/Parameters.cpp).

Offline checks: `python3 -m unittest discover -s machines/head/msa -p test_databases.py -v`. Local miniature UniRef/environmental fixtures also exercised conversion-only, repeated conversion and subsequent full CPU indexing with the exact pinned binary: both reported two representatives and two members totaling 152 residues each, and full hashes confirmed that indexing left every converted file unchanged. The unmodified official API separately completed environmental/unpaired and paired searches and template retrieval on a miniature full index. These fixtures validate runtime compatibility only; they do not create a production receipt, qualify the full corpus, or establish public/private scientific parity. Production installation and target-specific comparison remain required.

For per-target audit retention, start `server.py proxy --audit "$OUT/api-audit"` and point the native client at `http://127.0.0.1:8081`. The proxy binds only localhost and forwards to the official backend on port 8080. It stores exact HTTP request and response bodies, status, timing and SHA256 values under unique exchange directories; credential headers are excluded from audit metadata. Responses spool to disk and commit before the caller receives completion, so stopping the worker immediately afterward cannot race that record. Backend errors and incomplete transfers remain distinguishable. Download responses contain the original result tarballs and template bundles without content rewriting.

Before terminating the worker, run `server.py export --audit "$OUT/api-audit" --config "$OUT/msa-server.json" --output "$OUT/api-jobs"`. Only ticket IDs observed in that target's traffic qualify. Their input FASTA, job metadata, remaining generated scripts, and result archives are retained with checksums; unrelated targets and temporary search databases are excluded. Successful archives already contain generated pipeline scripts. Run export on failure as well to retain scripts from incomplete searches. Raw artifacts can contain input sequences and should follow the same access policy as native prepared inputs. Additional proxy tests use `python3 -m unittest discover -s machines/head/msa -p test_server.py -v` and cover disconnected callers and truncated upstream transfers.
